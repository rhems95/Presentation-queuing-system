02Introduction

  • PECIT student offices handle payments, records, and DMO transactions.
  • Clients currently wait in a manual first-come-first-served line.
  • Problems: unclear order, line cutting, weak priority handling, crowding, and no shared view of who is waiting.
  • This study built a LAN-based kiosk system that does not need continuous internet for daily queue work.

The problem is not the absence of computers. Arrival order in a physical line is the only queue rule.

04General problem

How can a standalone kiosk-based queuing management system with a thermal printer be developed and implemented to replace manual first-come-first-served lining with an organized, monitored, and coordinated queue process at PECIT?

05Specific problems

  1. 01How can Cashier, Registrar, and DMO transactions be organized instead of a manual line?
  2. 02How can a request be checked (Student ID or authorized walk-in) before a number is given?
  3. 03How can the client get an 80mm ticket, and how can priority be fair when several windows share one queue?

06Objectives

  1. 01Develop a standalone kiosk system for Cashier, Registrar, and DMO.
  2. 02Confirm with Student ID or authorized kiosk-PIN walk-in before numbering.
  3. 03Print an 80mm ticket and call 2 Priority → 1 Regular across shared windows.
  4. 04Provide a real-time public display and staff monitoring.
  5. 05Evaluate with testing, expert review, and UAT (ISO/IEC 25010-aligned).

Later slides map back to these five. This study does not claim a measured drop in waiting time.

07Scope and delimitation

In scope

  • Cashier, Registrar, DMO
  • 3-step kiosk, walk-in PIN path, 80mm print
  • Call Next, Recall, Complete, Hold, Call Held
  • Cashier 1–3 share one waiting queue
  • Admin users, students, PIN, done-only reports
  • LAN / Laravel 12 / MySQL

Out of scope

  • Online reservation, mobile app, SMS, cloud admin
  • All campus offices
  • RFID/NFC capable
  • A second student ticket while one is still in the queue

Built for PECIT Cashier, Registrar, and DMO on a local LAN — not an online reservation product.

10Methodology

  • Model: Waterfall — requirements, design, implementation, testing, deployment
  • Modules: Student Kiosk · Staff · Administrator · Queue Display
  • Rules: a student cannot get a new ticket while one is still in the queue · many walk-ins · Hold is not Complete · reports count done only
  • Evaluation: functional tests, one technical expert, UAT (ISO/IEC 25010-aligned, not a certification)

Waterfall fits a defined campus process: lock the queue rules first, then build and test them.

11System architecture

If the internet drops, the queue can still run on the local network.

12Kiosk and ticket

  • Step 1: Cashier, Registrar, or DMO (Promissory Notes hidden on the public kiosk)
  • Step 2: Regular or Priority
  • Step 3: Student ID keypad — lookup must succeed before Confirm
  • Walk-in: corner control asks for the PIN every time; no Student ID; many walk-ins allowed
  • A student is blocked from a new ticket only while one is still waiting, serving, or held — not one ticket per day
  • Ticket is number only. Optional one line for estimated minutes when history is enough
  • Printer: 80mm XP-58 (XP-Q90EC)

A name may appear on confirm so the student can check it. It is never printed.

13Staff, fair call, and Hold

  • Call Next locks the service, then claims the next ticket — no duplicate on Cashier 1 and 2
  • Order: 2 Priority → 1 Regular across windows of that service
  • Each window keeps its own open ticket and timer
  • Hold leaves Now Serving and is not counted as served
  • Call Held resumes at this window and skips 2 Priority → 1 Regular
  • Staff sees the student name or Walk-in (reason)
2 Priority → 1 Regular

Hold is not Complete. Held tickets leave Now Serving and are not counted as served.

14Public display

  • Now Serving and waiting in the same fair order, maximum 10
  • No names, no held tickets · optional voice

The public screen stays number-only. Staff may see a name while serving.

15Administrator

  • Users — one staff per window; Guard cannot log in
  • Students allowlist / CSV · kiosk PIN in settings · done-only reports

Admin sees the same 2 Priority → 1 Regular waiting order as staff, per service.

18Conclusions

  1. 01A standalone kiosk can replace the manual line at the selected offices.
  2. 02Confirmation (Student ID or PIN walk-in) works before numbering.
  3. 03The ticket is a clear reference; 2 Priority → 1 Regular is fair on shared windows.
  4. 04Display and staff panel give a real-time number-only view.
  5. 05UAT 4.55 supports acceptance under ISO/IEC 25010-aligned items.

A practical replacement for the manual line. No claimed measured cut in waiting time.

conclusions

19Recommendations

  • Deploy the kiosk, printer, display, staff PCs, and LAN as specified.
  • Orient staff on Confirm errors, walk-in PIN, Hold, and Call Held.
  • Keep the student allowlist and PIN current; back up the local database.
  • Use done-only reports; do not treat Hold as Complete.
  • Later, record actual wait and service times if PECIT wants a measured comparison.
  • Future work is not built: SMS, QR status, remote reserve — still no names on print or display.
